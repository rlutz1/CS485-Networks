## http, cookies

GET request
1. initial gets the webpage
2. then you load all the objects on the page
3. full page displayed

cookies are returned and stored on the client browser when created on the server
 -> cookie specifically for ny times -- **first party cookie**
 -> an ad on the NY times page, grabbing from an ad server -- has its own unique cookie on you; **third party cookie**
  -> if you are getting the same ad on another site (socks.com), the ad server now knows that you visited socks.com (bc you have the ad server cookie on your browser)
  -> now if you visit ny times again and ny times has an ad from that ad server, you may get an ad about socks! because your cookie info now has the ny times and sock.com traffic


getting ads and stuff -- usually an http get from your client browser, but can be invisible (an invisible link?)


**GDPR** -- this is why we get asked to confirm cookies. general data protection regulation, EU legality for privacy

**cookies v fingerprinting**
+ cookies are unique ids stored on device.
  + explicit data stored.
  + if this person wants darkmode, remember this for this user
+ fingerprinting is figuring out things about you based on passive signals, such as timing, browser version, installed fonts, timezones... 
  + much less control over this, cookies can be deleted, not much you can do about this
  + the metadata about you as a user.
  + lots of inference from data here.
  + if the user's browser wants dark mode by default, use dark mode

## CDNs

video streaming! most of internet traffic (80%)

challenges
+ scaleability -- billions of users!
+ heterogeneity (different used have different capabilities/network issues)

videos just sequence of images displayed at constant rate. 
+ sometimes frames are very similar, but a higher frame/sec is smooth
  + compression: **spatial** -- these 60 pixels are purple -- save this only
  + compression: **temporal** -- save the DIFFERENCE between frames (based on the probability that frames are similar one to the next)
  
but still a shit load of content to billions of people

store multiple copies of a single video across multiple sites 
+ avoids single point of failure
+ lessens the hops needed

types of cdn architecture TODO
+ **enter deep** push cdn servers deep into many access networks (akamai)
+ **bring home** smaller number of larger clusters of POPs near access nets (limelight)

netflix -- CDNs: OpenConnect CDN nodes
+ store copies of content at each of the nodes
+ don't have to go all the way to netflix servers, just need to find the closest copy server
+ avoids conjested links by allowing for travel to other servers in high traffic times.
+ storing copies on a cdn only, not implementing own infrastructure like google/tier 1

## socket programming

udp -- no connection, unreliable (lost, received out of order), faster

tcp -- connection, reliable, slower
+ tcp note that client closes socket AND server closes connection; udp the client only closes socket, server does nothing.

## transport layer intro

things we'll look at
+ multiplexing/demultiplexing
+ reliable data transfer
+ flow control 
+ congestion control

app layer -> defines rules and messages for a specific app (http, dns, smtp)
+ dns is in the app layer because it's about the human facing hostnames -- nothing else cares about that!
  + also very complicated.

transport layer -> only cares about HOW we move that shit ^^ between processes
+ takes a message, slaps on a header, now a segment
+ passes off to IP -- network layer.

**multiplexing** -- adding headers and crap when sending

**demultiplexing** -- removing all that shit on receipt
