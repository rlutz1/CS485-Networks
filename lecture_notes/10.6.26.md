**sequence number** -> correlating to what I am sending
+ this at some point becomes the ack number.

**acknowledgement number** -> correlating to what the receiver is READY to receive

+ tcp doesnt specify how out of order packets rceived -- up to implementor?
  + *buffer* or *trash*

**triple duplicate acknowledgement**

imagine you lose second packet of 5
+ we get ack's for packet 2 4 times!
+ tcp -> if it gets 3 duplicate acks with the name number, resend from that second packet!
  + "fast retransmit"
  
**flow control** -- controlling traffic between A and B (1 sender, 1 received) -- don't firehose B
+ receive window -- how many bytes receiver willing to accept
  + if 0 -> just send through probes until not 0, then send through data

**congestion control** -- controlling traffic on the network as a whole (n senders, n receivers)
+ receive buffer cannot alone solve this

**tcp handshake** -- 3 way SYN->SYNACK->ACK

throughput -- looking at all data that B receives

goodput -- USEFUL data the receiver gets and actually needs/uses
+ tcp has a slow start, and sends more and more over time.
+ cliff -> throughput = 0; delay = inf
  + knee -> throughput increases slowly, delay increases fast.
    + ideal point is right around the knee in terms of congestion control

network assisted congestion vs non-network assisted
+ assisted -> get feedback from routers explicitely
+ non-assisted -> transport takes responsibility for this
  + TCP -> staggers the amount of sending segments rate -- additive increase -- and then drop off
